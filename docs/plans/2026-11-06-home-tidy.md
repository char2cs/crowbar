# Home tidy: what a Crowbar home keeps, and for how long

Status: decided 2026-11-06 (owner delegated the policies). Each section names the
owner of the state, the rule, and how to roll back.

## 1. Backups: one compressed, verified image, pruned once superseded

- Format: `<home>/migrate/backups/<run-id>.tar.gz` (built as `<run-id>.tar.gz.partial`,
  renamed when whole). It holds, under their home-relative names, `state/` (minus
  `state/.lock`), `LAYOUT` and `migrate/ledger.jsonl` as they stood before the run,
  plus any path outside `state/` a pending plan names in `Plan.BacksUp` (the chat-ledger
  step names `chats/*/prompt-requests`). Entries are 0600 files and 0700 dirs.
- Verified before it is committed: each entry's SHA-256 is taken while it is copied,
  then the archive is read back and compared. A backup that does not read back is
  removed and the run halts in preflight. The disk preflight is unchanged (raw size
  plus 64 MiB).
- Retention (owner: `core/migrate`, at `Begin`, under the home lock): when the ledger's
  latest run ended `completed`, every backup but the newest is deleted, tarball or the
  older directory form. Never while a run is dangling, failed or interrupted, and
  never the backup in force. Steady state: one backup, the image taken immediately
  before the most recent migration that rewrote `state/`.
- Visibility: the boot log names each backup taken and pruned with its path and
  size; `crowbar migrate --plan` lists the backups on disk; `migrate/backups/README.txt`
  says how to restore.
- Restore (rollback): quit Crowbar, then
  `cd <home> && rm -rf state && tar -xzf migrate/backups/<run-id>.tar.gz`.
  That puts back `state/`, `LAYOUT`, the ledger and the backed-up journals together,
  so the next boot of a newer build runs the steps again; an older build finds the
  pre-migration home. A directory-form backup restores as before (copy its three
  entries back).

## 2. Retire the legacy databases (S8, R12): step 10 `retire-legacy`

- Owner: the migration catalog. Pre-open, in-layout at layout 1, recurring; it sits
  behind the layout bump (3), so a build that knows only layout 0 halts instead of
  re-creating the files empty (R12).
- Legacy set: `state/{events,store}/{agent_activity,agent_activity_snapshots,agent_runner,
  agent_runner_snapshots,node,node_snapshots}.db` with their `-wal`/`-shm`,
  `state/upgrades/`, `chats/*/prompt-requests/` (6), and `bin/crowbar` (9).
- It deletes only when all hold, decided from the ledger, never from a clock:
  (a) a run already completed at layout 1, so this is at least the second boot of the
  migrated home, after one whose post-open steps ran on the open stores;
  (b) the chat-ledger step owes no chat a retry;
  (c) each file is byte-identical to its copy in the newest backup (`-shm` excepted,
  it is a cache SQLite rebuilds; `bin/crowbar` excepted, it is a binary copy).
  A file that fails (c) is kept and noted, and not hashed again until it changes.
  Steps that read a legacy file open it read-only (`immutable=1`, or `mode=ro` beside a
  WAL), so reading never makes (c) fail.
- It does not set `RewritesState`: the backup it relies on stays the pre-migration
  image, and (c) is what makes deleting safe.
- Rollback after retirement: the restore in 1. A develop build run on a retired home
  without restoring sees chats with no history (it ignores `LAYOUT`); the README says so.

## 3. LAYOUT: step 9 `ledger-layout` bumps 0 → 1

- The catalog's first bump, after every in-layout step at layout 0; post-open steps
  move to layout 1. The engine writes `LAYOUT` when the bump completes, so a home this
  build has booted says `1`. A home at a newer layout halts with `layout_newer` and the
  web shows the halt page. Develop has no engine and never reads `LAYOUT`.

## 4. Attachments: one owner, keyed by chat id

- Home: `<home>/chats/<chat-id>/attachments/`, resolved from the chat id alone, so it
  survives a workspace move and goes when the chat's directory is reaped on delete
  (conversation `forget`). Deleting a workspace purges its chats, so their attachments go.
- Step 8 `chat-attachments` (pre-open, in-layout at layout 0) moves every
  `projects/**/chats/<chat-id>/attachments` to the new home by rename, checkpointed per
  chat; a name already present at the destination is kept at the source and noted.
  It is outside `state/`, so it needs no backup; rollback is moving the directory back.

## 5. Empty directories

- Content shards (`state/content/xx/yy`) are removed by the blob store's `Collect` when
  it deletes their last blob; runner and chat directories are created on first write and
  their parents pruned when the last child is removed.

## 7. Modes

- Every file Crowbar writes under the home is 0600 and every directory 0700, set where
  each is created. SQLite files are created 0600 by the store opener before SQLite opens
  them, so `-wal`/`-shm` inherit 0600; an existing file is narrowed at open. User
  checkouts under `projects/**/worktree` are git's and are left alone.
- Step 11 `owner-only` (pre-open, layout 1, runs once) narrows what an older build
  left with the umask anywhere else under the home (`descriptors/`, caches, project
  scaffolding). Rollback: none needed, an older build reads owner-only files.

## 8. MCP token off argv

- The runner token reaches `crowbar mcp` through `--token-file {tmp}/mcp.token` (0600,
  in the runner's tmp dir that is removed on exit and swept at boot), never argv.

## 9. No binary copy in the home

- Descriptors run the daemon's own executable (`os.Executable`, resolved once at boot)
  instead of a 59 MB copy in `<home>/bin`; step 10 removes an older copy.
