## 1. Crate map

Dependencies flow one way, from a higher layer to a lower one. Crates in the same layer never depend on each other. Logic crates never depend on `gpui`: only `ui`, the L3 views and the binary use it. `webview` is the one crate that binds `wry`, `gtk` and `webkit2gtk`. A crate may skip layers downwards.

### Dependency problems today, and how the map removes them

1. **Logic crate on gpui.** `shell_data` (daemon data, no UI) depends on the gpui crates `sidebar` and `settings_ui`, because it implements their source traits and builds their row types. The map splits each of them into a gpui-free crate (`sidebar`, `settings`) and a view crate (`sidebarview`, `settingsview`). `store` depends only on the gpui-free halves (manifest rule 20: the shared contract goes into a third, lower package). Every item `shell_data` imports was traced through its `use crate::` closure: none is gpui-bound once five presentational methods (`AvatarTint::color`, `WorkspaceStatus::glyph`, `IconTheme::glyph`/`folder_tint`, `DockSide::toast_side`/`docked_toasts`, `From<ui::Pose> for AfterMerge`) move to `sidebarview` as free functions.
2. **Same-layer edges.** `docs/rust-style.md` M17 defines three tiers (`app/crates` <- `app/desktop/crates` <- `app/desktop/app`). Under M16 ("crates in the same layer never depend on each other") most edges today are same-tier edges: `model`, `transport` and `browser_agent` on `protocol`/`atomic_file`/`browser_nav`; `pane_host` on `webview`; `terminal_session` and `terminal_view` on `terminal`; every view on `ui`; the four dialog views on `shell_data`; `shell_data` on `sidebar`/`settings_ui`; `sidebar_gallery` on `sidebar`. The five layers above make every edge point down. M17 and the `cargo-layer` check in `tools/scripts/check-rust-rules.sh` must be rewritten to this layer table (section 8, decision 1).
3. **`unsafe` outside a platform layer.** `webview` (two `borrow_raw` calls, plus one in a test) and the binary (`std::env::set_var`/`remove_var`) hold `unsafe`. All of it moves to `platform` (section 3).
4. **Disk access in a view crate.** The gpui `sidebar` wrote its preferences file through `atomic_file`. The preferences store and its disk adapter move to the gpui-free `sidebar`.
5. **Cycles.** Cargo forbids crate cycles; there are none. `tools/scripts/check-cycles.py` finds no file-level module cycle today. Grouping files into directories would create some directory-level cycles; each crate section names them and the placement that avoids them.

## 2. Rules for every crate

### 2.1 Module layout
- Modern layout: `src/foo.rs` is the root of module `foo`; its children live in `src/foo/`. No `mod.rs` (lint `mod_module_files`).
- Modules are cut by responsibility or feature (`tree/`, `panels/`, `drag/`, `pages/`, `relay/`), never by kind (`types/`, `traits/`) and never by line count.
- A module owns its types, its private children, the adapters of its own ports and its tests.
- A folder holds at most 12 modules. A `foo.rs` + `foo/` pair counts as one module. Every folder in the tree below meets this (checked by script over the mapping; the deepest folders hold 12).
- A module root that holds logic is imported by path from its children (`super::reply`), never through its own re-exports, so `check-cycles.py` sees no child -> parent -> child loop.
- New glue roots (a `foo.rs` with only `mod` and `pub(crate) use` lines) have no old file; each crate section lists them.

### 2.2 What roots expose
- `lib.rs` holds only `//!` docs, private `mod` lines and `pub use` (M10, M14). It re-exports the entry, `Error` (and `Result`), the traits, and the types used in their signatures. Nothing else is `pub`.
- A module root exposes to its siblings, as `pub(crate)`, only what a sibling uses. Everything else is private. Sub-modules are never `pub mod`, with one exception: the `ui` token modules (`font`, `layer`, `radius`, `shadow`, `spacing`, `text_size`, `timing`) are the API as module paths (`ui::radius::SM`, section 4.4). `lib.rs` re-exports them by `pub use`, but Rust only re-exports a module that is declared `pub` (E0365), so `foundation/tokens.rs` declares exactly these seven `pub mod` inside the `pub(crate)` module `tokens`; nothing else in the workspace is `pub mod`.
- Public types have private fields (C-STRUCT-PRIVATE). Where a split crate's view reads a field that is `pub(crate)` today, the field becomes private with a getter.
- Items that are `pub` today but used only inside their crate become `pub(crate)`; each crate section lists them.

### 2.3 Entry files (M10 together with M8)
M10 puts the entry in a file named after the crate; M8 (and the `type-name` check) puts a type in a file named after the type. With one-word crate names both only agree when the entry is a function or a one-word type. The rule:
- An entry **function** lives in `src/<crate>.rs` (`atomicfile::write`, `browser::resolve_address`, `browseragent::run_peer`, `diagnostics::start`, `platform::open_external`, `ui::init`, the `protocol` codec). This is what the `entry-file` check enforces.
- An entry **type** lives in the file named after the type: `src/layout.rs` (`Layout`), `src/transport.rs`, `src/terminal.rs`, `src/supervisor.rs`, `src/keymap.rs`, `src/store.rs` (`Store`), `src/pane_host.rs` (`PaneHost`), `src/window_state.rs`, `src/terminal_view.rs`, `src/layout_view.rs`, `src/tab_bar.rs` (`TabBar`), `src/ide_shell.rs`, `src/terminal_sessions.rs`, `src/settings_modal.rs`, `src/sidebar.rs` (`Sidebar`, in `sidebarview`), `src/browser_bar.rs`, `src/host.rs` (`webview::Host`), `src/client.rs` (`daemonapi::Client`), `src/chord.rs` (`chord::Chord`), and `src/view.rs` for `startup::View`, `oobe::View`, `pairing::View`, `branchimport::View` and `folderpicker::View`. The entry's own child modules live in the folder of the same name.
- A type named after its crate (`panehost::PaneHost`, `windowstate::WindowState`, `terminalview::TerminalView`, `chord::Chord`) is the manifest's allowed `vault.Vault` case (rules 11 and 23), not stutter. A type that adds a word to its crate's name (`OobeView` in `oobe`, `RemoteFolderPicker` in `folderpicker`) is stutter and becomes `View`.
- A crate without a single entry (`sidebar`, `settings`) has no `src/<crate>.rs`; its README names the entry ports.

### 2.4 Naming
- **Crates.** Manifest rule 21: "Package names are short, lowercase, singular nouns, with no underscores." `docs/rust-style.md` M21 maps it as "short, lowercase `snake_case`, no stutter". A single lowercase word is valid snake_case and satisfies rule 21, so the convention is: **one lowercase word, no `_`, no `-`**. Two words are joined without a separator only when one word cannot name the job (`atomicfile`, `browseragent`, `ptysession`, `windowstate`, `folderpicker`, `branchimport`, `viewtabs`, `ideshell`, `daemonapi`), Go style (`filepath`). The folder name equals the package name.
- **The `view` suffix.** A gpui crate is named `<feature>view` only when a gpui-free crate of the same feature exists: `terminal`/`terminalview`, `layout`/`layoutview`, `sidebar`/`sidebarview`, `settings`/`settingsview`. Other gpui crates are named for what they draw (`viewtabs`, `ideshell`, `browserbar`, `startup`, `oobe`, `pairing`, `branchimport`, `folderpicker`).
- **Binary.** The package `crowbar_desktop` becomes `crowbar` (its binary is already `crowbar`). Binary targets inside crates: one gallery per view crate, named `<crate word>gallery` (`uigallery`, `sidebargallery`, `settingsgallery`, `terminalgallery`, `tabsgallery`, `startupgallery`) so that every binary of the workspace has its own name, and the test-only `fake_daemon`.
- **Modules and folders.** Short lowercase snake_case nouns named for what they own; one word where one word is enough. A module whose name equals a dependency crate (`browser`, `settings`, `sidebar` inside the binary) is allowed; its parent then writes the crate path as `::sidebar::Sidebar`. Inside `store`, the settings module is `settings_core` and the sidebar modules are `sidebar_view` and `sidebar_commands` (named after their types) to avoid that ambiguity in `lib.rs`.
- **Files.** A file is named after its one type in snake_case (M8), or after the concept its free functions serve. `error.rs` holds `Error`.
- **Banned in any crate, folder or file stem:** `util(s)`, `common`, `helper(s)`, `base`, `misc`, `support`, `shared`, `data`, `info`, `tmp`. The exceptions are the names the rules gate itself requires: `src/test_support/`, `tests/support/`, `tests/support/real_infra/` (M41, M43). Platform API terms keep their platform name (`browsing_data` for WebKit website data, `data_store` for `WKWebsiteDataStore`).
- **No stutter.** No folder or file repeats its parent folder or its crate: its first word is not the parent's first word, and it does not start with the crate name (`sidebar/src/rows/row_label.rs` becomes `rows/label.rs`, `store/src/live/held/entity_store/` becomes `held/entities/`). The fix, in order of preference: rename a free folder (`ui` `control/text/` -> `control/editor/`, `terminal` `links/` -> `hyperlink/`); move a file up beside the type it serves (`ui` `overlays/overlay_id.rs` -> `floating/overlay_id.rs`); rename a pub(crate) type with its file (`HostEntry` -> `hosts::Entry`). The one exception is a stem that is the type name the `type-name` check requires for a type re-exported from the crate root (`ui` `button/button_size.rs`), plus `WrappedSurface`, whose bare name collides with `ui::Surface`; each such line in the mapping says so (47 files), and the crate sections list them. A `pub(crate)` type whose name repeats its folder is renamed with its file. A type re-exported from the crate root keeps its name when the plain word would read badly from the root (`terminal::SearchOptions` stays; `ui::ButtonSize` stays rather than `ui::Size`), per M23. Crate-stutter renames (`TerminalConfig` -> `terminal::Config`, `LayoutHistory` -> `layout::History`, `WebViewHost` -> `webview::Host`, `StartupView` -> `startup::View`) are listed per file in the mapping. 159 files carry a type rename.

### 2.5 Adapters
The rules gate exempts direct clock reads and direct file access only under a directory named `adapters/` (`direct-time`, `direct-fs` in `tools/scripts/rust-rules.awk`). So an adapter lives in `<owning module>/adapters/`, next to the port it implements. No crate keeps a crate-wide `adapters/` bag (`atomicfile`, whose whole job is the disk write, keeps `src/adapters/disk_write.rs`).

### 2.6 Tests, benches, galleries, features
- **Unit tests** stay inline in each file (`#[cfg(test)] mod tests` at the bottom, M42). Moving a file moves its tests.
- **Shared unit-test fakes** live in `src/test_support/` declared once in `lib.rs`, or at the lowest module that uses them (`src/<module>/test_support.rs`, manifest rule 19). A `test_support/` folder that held one file becomes a single `test_support.rs`.
- **Integration tests** stay in `tests/<concern>.rs` with fakes in `tests/support/` and real-infrastructure fakes in `tests/support/real_infra/`. `tests/<name>.rs` needs `src/<name>.rs` or the crate name (M43), so `model/tests/model.rs` becomes `layout/tests/layout.rs`, `daemon_supervisor/tests/daemon_supervisor.rs` becomes `supervisor/tests/supervisor.rs`, and `transport/tests/remote.rs` becomes `tests/pairing.rs`.
- **Galleries.** Each view crate has at most one demo binary, `src/bin/gallery/main.rs` plus sibling modules: `ui` (`uigallery`), `sidebarview` (`sidebargallery`, was the `sidebar_gallery` crate), `settingsview` (`settingsgallery`, was `settings_preview`), `terminalview` (`terminalgallery`, was `examples/terminal_demo`), `layoutview` (was `layout_demo`), `viewtabs` (`tabsgallery`, was `tab_bar_demo`), `startup` (`startupgallery`, was `startup_gallery`). A gallery that needs fakes or extra dependencies declares `required-features` (`sidebarview`: `fixtures`; `settingsview`: `settings/fake`; `terminalview`: `gallery`, turning its former dev-dependencies into optional ones).
- **Test-only binary:** `supervisor/src/bin/fake_daemon.rs` (feature `test-daemon`), unchanged.
- **Benches:** `terminal/benches/bulk_output.rs` with `benches/adapters/stopwatch.rs`, unchanged.
- **Fixture features:** `sidebar` keeps `fixtures` (`DemoShell`, was `DemoData`); `sidebarview` forwards it. `settings` gets `fake` (`FakeBackend`), because unit tests of both settings crates and the gallery need the same fake. `webview` keeps `mock`.

### 2.7 README per crate
Every crate gets `README.md` at its root with three headings: **Owns** (one paragraph), **Public interface** (the `lib.rs` exports with one line each), **Depends on** (workspace crates and why). `platform` adds **Unsafe** (every block, its file, its SAFETY argument and its test). Each crate section in section 4 gives the outline.

## 3. Platform layer and every `unsafe`

All `unsafe` of the desktop app ends up in crate `platform`, one minimal layer per OS: `src/macos/` (AppKit, WebKit) and `src/linux/` (X11, GTK). Rules:
- `platform` is the only desktop crate with `#[expect(unsafe_code, reason = "...")]`, on each function that holds a block. `docs/rust-style.md` line 106 names `webview` as the exception; it changes to `platform`.
- Each block does one unsafe operation (`multiple_unsafe_ops_per_block`), carries a `// SAFETY:` line, sits behind a safe type or function, and keeps a unit test.
- The crate README lists every block under **Unsafe**.
- Prefer the safe `objc2` bindings (`objc2-foundation`, `objc2-app-kit`) over raw messages. The macOS web view code already uses `objc2-foundation` safely.
- Recommended gate rule (`unsafe-home`): reject `unsafe` outside `app/desktop/crates/platform/src/{linux,macos}/`, with `app/mobile/ios-plugin/src/ffi.rs` as the one listed exception.

Every hit of `git grep -n 'unsafe' -- 'app/**/*.rs' ':!app/desktop/vendor'`:

### 4.1 Shared crates (`app/crates`)

#### atomicfile
Replaces a file all-or-nothing. L0. Deps: tracing.

```
src/            (3)  lib.rs, atomicfile.rs (entry: pub use of write)
  adapters/     (1)  disk_write.rs (the disk write; direct-fs is exempt only under adapters/)
```
- `lib.rs`: `pub use atomicfile::write;`
- README. Owns: staged write, fsync, rename over the target, directory fsync, owner-only mode. Public interface: `write(path, bytes)`. Depends on: nothing in the workspace.
- Notes: the layout is today's, renamed. The write stays under `adapters/` because the rules gate allows direct file access only there.

#### browser

#### Notes on the sidebar split
**Layer violation today.** `sidebar` is one gpui crate, and `shell_data` (the future logic crate `store`) imports about 50 of its types, so it pulls in gpui. The split removes that. Five gpui-free types reach `ui`/`gpui` through one method each, and the method moves to the view:
- `AvatarTint::color` goes to `column/mark_view.rs`.
- `WorkspaceStatus::glyph` goes to `parts/row_glyph.rs`.
- `IconTheme::glyph`/`folder_tint` go to `file_tree_row/glyph.rs`.
- `DockSide::docked_toasts`/`toast_side` go to `overlays/toasts.rs`.
- `impl From<ui::Pose> for AfterMerge` goes to `changes/merge_draft.rs`.

**Pure rendering details** stay in the view even without gpui, because only the views read them: `Check`, `Tone`, `TileShape`, `MenuStep`, `EditOutcome`, `LabelVisibility`, `FrameGeometry`, `FileTreeEntry`, `TreeLook`, `MatchDirection`, `SidebarEvent`, `Clock`. `DragState` and `DropHint` hold gpui `Point`/`Bounds`, and `MenuEntry`/`MenuCursor` hold `ui::IconName`, so the menu model and the drag state stay in the view.

**Module cycles.** There are none at file level today (SCC check over every `use crate::` edge). In the new tree:
1. Logic `frame <-> tree` exists only through `frame/metrics.rs`. Fix it by moving `REMOVAL_DRAIN_SECONDS` into `deletion/removal_tray.rs`, `DRAG_THRESHOLD` into `reorder/drag_arm.rs` and `EDGE_BAND`/`EDGE_SPEED_MAX` into `reorder/edge_scroll.rs`. The pixel constants only the views use (`FOOT_HEIGHT`, `TRAFFIC_LIGHT_RESERVE`, `SWITCHER_HEIGHT`, `ROW_*`, `INDENT_STEP`, `HANDLE_HIT`) move to `sidebarview/src/sidebar/scale.rs`.
2. The view keeps one hub. `sidebar.rs` holds one state value per surface (`DragState`, `RowBounds`, `FileSearch`, `Field`, `MergeDraft`, `SpaceDraft`, `Scrolls`, `IconEditor`, `OpenMenu`, `Peek`), and each surface extends `Sidebar` with `impl Sidebar` blocks, so every surface <-> `sidebar` edge goes both ways. Surfaces call each other only through `Sidebar` methods. Apart from the hub, the tree removes the sibling cycles a naive grouping creates:
   - `filter_menu` moves into `popup/`, because `menu_ops` rebuilds it while it is open.
   - `DragPoint`/`DragPress` sit under `sidebar/row_action/`.
   - `FileTreeEntry` sits beside `file_tree_row`, not under it.

   Recommendation: make each panel its own `Entity<…>` child view in a later change. Grouping cannot remove the hub.

**Deleted.** Nothing. The crate-wide `adapters/` bag is split: `disk_preferences` moves to `frame/preferences/adapters/disk_storage.rs` (owner of the `Storage` port) and `system_clock` to `sidebarview/src/sidebar/clock/adapters/system.rs`. Checks for code to delete:
- No strip or palette code is in these crates. `icon_theme.rs` was added by strip commit `d6a735022`, but it is the Files `iconTheme` setting: Tauri has it and store reads it, so it is kept.
- No `unsafe`, no `allow(dead_code)`, no test exemptions.

**Dead code.** `DemoData::with_running_agent` (`demo_data.rs`) has no caller: delete it. `drag_started`, `allowed_modes` and `edge_speed` are `pub use`d today with no outside user. After the split the view calls them, so they stay public.

**Type renames** (stutter or banned name only):
- `SidebarData -> Source` (crate stutter plus the banned word `data`)
- `CommandSink -> Sink` (under `command/`)
- `TreeState -> Tree` (holds the module root `tree.rs`)
- `PreferenceFile -> Storage`, `DiskPreferences -> DiskStorage`, `MemoryPreferences -> MemoryStorage`
- `DemoData -> DemoShell` (banned word `data`)
- `SidebarEvent -> Event`, `FrameGeometry -> Geometry`, `EditOutcome -> Outcome`, `InlineEdit -> Field`

`store` and the app must follow the `Source`/`Sink`/`DemoShell` renames.

**fixtures feature.** It survives the split like this:
- `sidebar` keeps `fixtures = []` with `#[cfg(feature = "fixtures")] mod fixtures;`. Its own dev-dependency on itself with `fixtures` lets the logic tests use `DemoShell`.
- `sidebarview` forwards `fixtures = ["sidebar/fixtures"]`, which the gallery bin requires. Its dev-dependency enables it for the view tests and their `Recorder`.

## 7. Migration order

A move commit is pure: `git mv`, `mod` and `use` path edits, `Cargo.toml` edits, and the visibility changes a move forces (`pub(crate)` to `pub` across a new crate boundary). No behaviour change, no deletion, no logic edit. Behaviour commits (deletions, strip removal, the IDE shell) are separate. Every commit builds with `cargo check --workspace --all-targets`, passes `cargo test --workspace` and `tools/scripts/check-rust-rules.sh`.

Re-keying the rules gate: `check-rust-rules.sh --rekey OLD NEW` moves a file's baseline entries and refuses a file with none. Today `tools/scripts/rust-baseline.txt` and `allow-baseline.txt` hold no `app/` entry, so no move needs a rekey. If an entry appears before the moves, run `--rekey` for that file in its move commit.

1. **Delete the command palette** (behaviour). The `command_palette` crate, the palette wiring and the `mod+shift+p` and `mod+,` table lines. Fewer files to move.
2. **Rename crates, leaves first, one commit per crate**: `atomic_file`->`atomicfile`, `browser_nav`->`browser`, `daemon_supervisor`->`supervisor`, `shell_diagnostics`->`diagnostics`, `shell_platform`->`platform`, `model`->`layout`, `browser_agent`->`browseragent`, `shell_keys`->`keymap`, `window_state`->`windowstate`, `terminal_session`->`ptysession`, `pane_host`->`panehost`, `tab_bar`->`viewtabs`, `layout_view`->`layoutview`, `terminal_view`->`terminalview`, `browser_chrome`->`browserbar`, `startup_view`->`startup`, `oobe_view`->`oobe`, `pairing_view`->`pairing`, `branch_import_view`->`branchimport`, `remote_folder_picker`->`folderpicker`, `shell_data`->`store`, `crowbar_desktop`->`crowbar`. Each commit renames the folder, the package, the `[workspace.dependencies]` key and every `use`. The last one also updates `Makefile` (`cargo run -p crowbar_desktop`), `.github/workflows/rust.yml` (`-p crowbar_desktop`), `app/crates/README.md` and the docs that name the crates.
3. **Move all `unsafe` into `platform`**: `appkit_parent.rs`, `xlib_parent.rs` from `webview` (which gains the `platform` dependency) and `env_change.rs`, `x11_session.rs` from the binary. Update `docs/rust-style.md` line 106.
4. **Split the layer violators**, one commit each, in this order:
   1. `sidebar` -> `sidebar` + `sidebarview` (gpui files go to the new crate; the five presentational methods become view functions; `sidebar_gallery` becomes `sidebarview/src/bin/gallery/`).
   2. `settings_ui` -> `settings` + `settingsview`, with the `fake` feature.
   3. `store` switches its dependencies to the gpui-free halves. After this commit no logic crate depends on gpui.
   4. `AppPhase` moves from `protocol` to `startup`.
   5. **Extract `chord`** (decision 6): `chord.rs`, `primary.rs` from `settings`, `keystroke.rs`, `modifier.rs`, `modifiers.rs`, `chord_text.rs` (as `keystroke/dom_key.rs`) from `keymap`. settings, settingsview, keymap and the binary gain the `chord` dependency.    6. **Extract `daemonapi`** (decision 7): the 18 files of `store`'s daemon module, plus a new `error.rs` with the five daemon variants that `store::Error` then wraps. ## 8. Decisions for the owner

The code and the Tauri app could not settle these. Each has a recommendation.

1. **Layer rule text.** `docs/rust-style.md` M17 knows three tiers; this map has five layers. Recommendation: replace M17 with the layer table of section 1 and make `cargo-layer` check it.
2. **Crate naming text.** M21 says "lowercase snake_case"; the manifest says "no underscores". Recommendation: amend M21 to "one lowercase word, no `_` or `-`", as used here.
3. **Layout schema version.** `SCHEMA_VERSION` is 2 only because of the strip groups migration. Recommendation: the GPUI shell has not shipped, so return to v1 and drop the migration. If v2 files must load, add a v2 -> v3 migration that keeps each group's active pane.
4. **`Tab`/`TabId` versus Tauri's "view".** Tauri calls the top tabs views (`views`, `viewOrder`, `viewId`); the IDE shell has tabs of its own. Recommendation: rename `layout::Tab`/`TabId` to `View`/`ViewId` so the two kinds of tab never share a name. Not in this mapping.
5. **View pins.** Tauri views can be pinned (`view-pins.ts`); the model has none and the strip pin code is deleted. Parity work adds a view pin to `Tab` and `Command`. Recommendation: do it after the IDE shell revert.
6. **One chord model.** `settings` (keys) and `keymap` both parse `mod+...` chords; both are L1, so neither may use the other. Recommendation: extract the chord type, its parser and the keystroke into a new L0 crate `chord` with no dependencies (`Chord`, `Primary`, `Keystroke`, `Modifier`, `Modifiers`), used by `settings` and `keymap` (and by `settingsview` and the binary for labels). No layer changes. Mapped in this plan: six files (section 4.6, `chord`). The default chord tables stay in `settings/catalog/keybindings.rs` and `keymap/shell_command/table.rs`; with one `Chord` type the binary's reconciliation compares parsed chords. Merging the two tables is a later change.
7. **One daemon client.** `shell_data` (its daemon client files) and `terminal_session` (`rest.rs`) each carry a daemon HTTP client. Recommendation: extract it now into the L1 crate `daemonapi` (deps: protocol), used by `store` and `ptysession`; `ptysession` moves to L2 so that edge points down. Mapped in this plan: the 18 daemon files of `shell_data` (section 4.7, `daemonapi`), plus a new `error.rs`. `ptysession` keeps its files; the duplicate envelope check inside `rest.rs` is deleted in its own commit.
8. **`Clock` twice.** `layoutview` and `viewtabs` hold the same `Clock` port. Recommendation: one `Clock` in `ui::motion` (the clock port already lives there).
9. **Unwired `PaneHost::display`.** The host computes placeholder and error frames that nothing draws. Recommendation: draw them in the IDE shell's pane body, as Tauri does.
10. **Strip-only app code kept for the IDE shell.** `panes/ide/tab_looks.rs`, the rename prompt and the tab path actions are reached today only through the strip menu. Recommendation: rewire them to the IDE shell tab menu in the revert; delete them if the IDE shell lands later than the revert.
11. **`sidebarview` hub.** `Sidebar` holds one state value per panel and every panel adds `impl Sidebar` blocks, so panel modules and the entry depend on each other. Grouping cannot remove that. Recommendation: make each panel its own child entity in a later change.
