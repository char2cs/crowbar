# Agent usecase decomposition

Status: DRAFT 1 — architecture. Not yet reviewed.

## 1. The measured problem

`api/internal/app/usecases/agent/` today:

| metric | value |
| --- | --- |
| production files (flat, no subpackages but `internal/termwait`) | 27 |
| production lines | ~7,400 |
| test lines | ~9,700 |
| `Usecase` struct fields | 22 |
| `New()` parameters | 12 |
| exported `*Usecase` methods | 46 |
| unexported `*Usecase` methods | 87 |

Nine of the 22 fields are not ports at all — they are stateful machinery types
declared in the same flat package and totalling ~1,960 lines: `promptJournal`,
`answerDesk`, `turnWaits`, `hookDeliveryJournal`, `messageStreams`,
`pendingRunnerHooks`, `catalogRuns`, `chatGate` (×2 instances), `chatWorkStates`,
`telemetryStore`.

So the package is two things fused: an orchestration layer, and the private
machinery that layer drives. Nothing separates them, so neither can be read.

## 2. The reference law

Two sources, and they agree.

### 2.1 `go-style` (project skill)

1. One parameter per line, always.
2. Max 2 indentation levels.
3. Early exits; happy path last; no `else`.
4. **One type per file**, file named `snake_case` after the type.
5. No comments on unexported symbols. Exported symbols get detailed doc comments.
6. Stateless singletons are package-level functions, not structs.
7. `NewXxx` only when there is real state to initialise.
8. **Expose interfaces, not implementations.**

### 2.2 quiver.core (read directly, this session)

Its usecases are thin because the *machinery is somewhere else*:

```go
type runtimeUsecase struct {
    arrow   arrowrepo.Arrow      // repository interface
    runtime runtimerepo.Runtime  // repository interface
    graph   graph.Graph          // repository interface
}
```

Observed rules:

- **One usecase per concern, not one per domain.** `Arrow`, `Runtime`,
  `Collection`, `Search`, `Discovery`, `Config` are six separate usecase types in
  one package, wired by `usecases.Container`. The largest interface has 10
  methods; `RuntimeUsecase` has 6. Ours has 46.
- **Every field is a port or one cohesive local concern.** `runtimeRepository`
  has 9 fields, but 5 are ports and the remaining 4 (`drainWg`, `drainMu`,
  `drainClosed`) are a single named concern. A pile of unrelated machinery
  structs is what does not appear.
- **Stateless procedures are package-level funcs in `internal/`, taking narrow
  parameters**, e.g. `runtimeinternal.RecoverTransients(ctx, listArrows, agg, wizard)`.
- **Stateful collaborators are interfaces in their own `internal/` package**,
  e.g. `assembler.Assembler`, built by `assembler.New(...)`.
- **Function-typed ports in `deps.go`** (`GetArrowFn`, `MarkInstalledFn`,
  `HasDependentsFn`) let a lower layer receive exactly what it needs without
  importing the layer above. This is the tool for breaking our `*Usecase`
  back-references.
- **`internal/commands/`, one command per file**, 43–90 lines each.

Our own `internal/engine/agents/` already obeys this: 76 files, 4,522 lines, one
concern per package. The engine is not the problem. The usecase layer is.

## 3. Target architecture

### 3.1 Shape

```
usecases/agent/
  agent.go              Agent facade: embeds the sub-usecase interfaces, New()
  deps.go               narrow function-typed ports (quiver.core deps.go)
  chats.go              ChatUsecase       — lifecycle + reads
  runners.go            RunnerUsecase     — spawn, resume, switch, boot reconcile
  prompts.go            PromptUsecase     — submit, slash catalog, delivery settle
  hooks.go              HookUsecase       — ingest, canonical event dispatch
  answers.go            AnswerUsecase     — human-in-the-loop decisions
  providers.go          ProviderUsecase   — catalog + preferences
  errors.go             sentinel errors + presentation codes
  internal/
    delivery/           promptJournal + hookDeliveryJournal + shared record write
    inflight/           chatGate, turnWaits, chatWorkStates, pendingRunnerHooks
    stream/             messageStreams, messageBuffer
    answerdesk/         answerDesk
    catalogrun/         catalogRuns
    telemetry/          telemetryStore
    termwait/           (already exists, unchanged)
```

Each `internal/` package exports an **interface** plus a constructor; the struct
stays unexported. One type per file, `snake_case`.

### 3.2 The facade

The API layer already depends on an interface it declares itself
(`handlers.AgentUsecase`, ~30 methods). To split the God object without any
blast radius outside the package, the facade embeds the sub-usecase interfaces
so their methods are promoted:

```go
type Agent struct {
    ChatUsecase
    RunnerUsecase
    PromptUsecase
    HookUsecase
    AnswerUsecase
    ProviderUsecase
}
```

`*Agent` then satisfies `handlers.AgentUsecase` by promotion. Requirement: the
six method sets must be **disjoint**, or the selector is ambiguous at compile
time. This is checked mechanically before implementation (step I-0).

### 3.3 Cross-usecase calls

Sub-usecases need each other (hook ingest records messages and moves turn state;
prompt submit displaces a runner). Two mechanisms, in this order of preference:

1. **Shared collaborator.** Both sub-usecases hold the same
   `internal/inflight.Turns` instance. No call between them at all.
2. **Narrow function port declared in `deps.go`.** e.g.
   `type OpenTurnFn func(ctx context.Context, chat domain.AgentChat, runner domain.AgentRunner) error`.
   Wired once in `New()`.

A sub-usecase must never hold `*Agent`, and must never hold another sub-usecase
as a whole interface. That is the rule that keeps the split real rather than
cosmetic.

### Why `internal/` and not the engine

`messageStreams` was the one real candidate for `engine/agents` — it interprets a
provider's hook stream. It stays in the app layer because it is keyed by
**chat id**, a concept the engine does not have; the engine is provider-shaped
(descriptors, spawn, hook vocabulary), not conversation-shaped. Moving it would
push a chat-keyed cache into a package that has no chats. Everything else in the
table is durable app state (journals) or process-local coordination (gates,
waits) — neither belongs in a provider engine.

## 5. Deduplication

Confirmed by reading:

1. **Durable record write.** `os.CreateTemp` → write → `Sync` → `os.Rename` →
   parent-dir fsync appears in `prompt_journal.go:462-498` and
   `hook_delivery.go:139-160`. Extract to `internal/delivery/record.go` as one
   generic writer. **This is the single clearest instance of the repetition the
   review called out.**

2. **Keyed mutex maps.** `chatGate`, `turnWaits`, `chatWorkStates`,
   `pendingRunnerHooks` are all `mu sync.Mutex` + `map[string]*T` with lazy
   creation. Whether they can share one generic depends on their differing
   signal/evict/refcount behaviour — resolved by the census in step I-0, not
   assumed here. Co-locating them in `internal/inflight` is worthwhile even if
   they cannot share an implementation.

3. Further candidates (chat+runner fetch preamble, error-wrap shapes) are
   pending the census and will be folded into draft 2.

## 6. Invariants that must survive

This branch's behaviour was live-verified and must not regress:

- Every assistant message of a turn is recorded, in order, with its own turn id,
  and tool calls attach to the right one.
- A message is visible BEFORE its turn ends.
- The terminating hook supersedes a lossy stream; a streamed reply is never
  recorded twice.
- A provider with no streaming hook records exactly what it always did.
- A slash command is sendable and never wedges the chat; delivery settles after
  quiescence with no turn.
- An unfinished message abandons its turn after the quiet window, recording the
  partial text.
- No descriptor declares a provider transcript read.
- Crowbar reads only a provider's outside surface.

The regression suite in `api/tests/` pins all of these and must stay green
without modification. **A test change is a red flag in this refactor**: the
public behaviour is not changing, so an assertion that has to move means
something broke.

## 7. Risks

| risk | mitigation |
| --- | --- |
| Embedded-interface method collision | mechanical disjointness check before any code moves (I-0) |
| White-box `*_internal_test.go` lose access to moved symbols | tests move with their package; the ~1,200-line `harness_test.go` stays |
| A "pure machinery" type turns out to touch `*Usecase` | census verifies each before its move; move order is zero-coupling first |
| Behaviour drift during mechanical moves | each move is a separate build+test gate; no logic edits in a move commit |
| Scope creep into the API layer | facade keeps the external surface byte-identical |

## 8. Staging

Ordered so that every stage ends green and is independently revertible.

- **S0** — census + disjointness check. No code changes.
- **S1** — move zero-coupling machinery: `inflight`, `stream`, `telemetry`.
- **S2** — `delivery` package + extract the duplicated record writer.
- **S3** — `answerdesk`, `catalogrun` (require splitting orchestration from machinery).
- **S4** — split the 46-method `Usecase` into six sub-usecases behind the facade.
- **S5** — style pass: one type per file, param-per-line, comment rules.

Gates after every stage: `go build -tags noEmbed ./...`,
`go test -tags noEmbed -race ./...` (164 packages), `golangci-lint run`,
integration vet. Full integration suite after S4 and S5.

## 9. Corrections established before draft 2

These are measured, not proposed. Draft 2 supersedes the sections they contradict.

### C1 — §3.1 and §4 put the journals in the WRONG LAYER (decisive)

Measured:

- quiver.core: **zero** usecase files import `os` or `path/filepath`. Its usecases
  never touch the filesystem. The atomic temp+rename write lives in the engine
  (`engine/vault/manifest.go:199-215`).
- Crowbar `usecases/agent`: **eight** files import them;
  `prompt_journal.go` makes 23 filesystem calls and `hook_delivery.go` 7.

So the two journals are durable stores sitting in the usecase layer. Moving them
to `usecases/agent/internal/delivery` relocates the violation one directory
deeper instead of fixing it. **They must become a repository**, alongside
`agentchat`, `agentrunner`, `agentactivity`, following the `agentrunner` shape
(`internal/commands/`, `internal/store/`). `repositories.Container` already
carries the sibling event stores and already uses plain-func injection from the
app layer, which is the same idiom as quiver.core's `deps.go`.

The remaining filesystem calls in the other six files are incidental
(`filepath.Join` for argv, `os.Environ`, one `MkdirAll`, one `RemoveAll`) and
stay.

### C2 — the keyed-mutex maps must NOT be unified

§5.2 floated one generic for the eight `mu + map[string]*T` types. The census
says no: they differ in ways that are load-bearing — `chatGate` refcounts and
evicts at zero, `answerDesk` reaps on a TTL timer, `messageStreams` is LRU-capped
at 64, `pendingRunnerHooks` uses explicit register/discard, `turnWaits` closes a
one-shot channel per entry. Forcing one generic over these would be the same
mistake in the opposite direction.

`chatGate` is already extracted and reused three times — the package does
already share when the semantics match.

The one real overlap: `turnWaits.changed` (`turns.go:41-76`) and
`chatWorkStates.states` (`turns.go:181-231`) implement an identical
lazy-map + close-and-recreate broadcast idiom. Those two, and only those two,
collapse into one `broadcastRegistry`.

### C3 — confirmed duplication, with line ranges

1. **Durable record write** — `prompt_journal.go:453-491` vs
   `hook_delivery.go:134-167`. Identical 7-step sequence; differ only in temp
   prefix, target filename field, and error phrasing. One asymmetry worth keeping
   in mind: `writePromptRecord` takes `syncDir` as an injectable parameter,
   `writeHookDelivery` calls the concrete helper, so its dir-sync failure path
   cannot be mocked. Unify on the injectable form.
2. **Descriptor resolution preamble** — the
   live-runner → `WorktreeDir` → `agents.Get` sequence repeats at
   `answers.go:456-467`, `catalog.go:69-86`, `prompts.go:184-199`,
   `ingest.go:76-91`, `switch.go:38-58`. A tighter two-step variant
   (`u.home()` → `u.agents.Get`) repeats at `terminal_wait.go:37-45` and
   `turn_stall.go:75-87`. Both dedupe; per-site error mapping stays caller-side.
3. **Reap-under-home block** — `chat.go:111-123` vs `agent.go:138-150`.

Not duplication, contrary to draft 1: there is only **one** directory-load
function (`readPromptRecords`, `prompt_journal.go:413-432`), and the 198 error
wraps are 192 distinct phrases — a missing-helper style gap, not repetition.

### C4 — a real defect found while measuring

`hookDeliveryJournal.completed` (`hook_delivery.go:41`) is written at line 106
and never deleted: an unbounded `map[string]string`, one entry per hook delivery,
for the life of the daemon. At the measured ~13 hooks per turn this grows without
limit. Fix it during the repository extraction — bounded retention, the way
`answerDesk` already reaps on a TTL.

### C5 — a correctness note

`readPromptRecords` (`prompt_journal.go:413-432`) does not skip malformed records
as its shape suggests: a JSON decode failure aborts the whole batch. Decide
deliberately during the move whether that is the intent.

### C6 — corrected counts, and the finding that de-risks the whole plan

§1 undercounted. Measured exactly:

| metric | draft 1 said | actual |
| --- | --- | --- |
| `Usecase` fields | 22 | **26** |
| `*Usecase` methods | 46 + 87 = 133 | 133 (confirmed) |
| other types in the package | ~10 | **32** |

The finding that matters: **all 32 of those types reference `Usecase` zero times.**
Not one machinery type — `answerDesk` (149 lines), `promptJournal` (297),
`hookDeliveryJournal` (65), `catalogRuns`, `messageStreams`, `turnWaits`,
`chatGate`, `pendingRunnerHooks`, `telemetryStore` — holds a `*Usecase`, takes
one, or names one.

Draft 1 recorded "answers.go: 17 Usecase-coupled refs" and "hook_delivery.go: 3".
That measurement was of the wrong thing: those are *`*Usecase` methods living in
those files* that touch `u.answers` / `u.hookDeliveries`. The **types** are clean.

Consequence: extracting every machinery type into `internal/` packages is a
mechanical move with no API redesign — no interface has to be invented to break a
back-reference, because there are no back-references. The risk in this refactor
is concentrated almost entirely in S4 (splitting the 133-method God object), not
in S1–S3.

### C7 — the concern clustering, from field-use data

Field use across the 133 methods:

- **Ports used everywhere** — `chats` 38, `runners` 29, `activity` 23, `ws` 17,
  `agents` 15. These cannot be partitioned; each sub-usecase will hold two to
  four of them. That is exactly quiver.core's shape (three ports per usecase),
  not a violation of it.
- **Machinery, already concentrated by concern** — `prompts` 13, `work` 12,
  `turns` 10, `answers` 7, `spawns` 7, `pendingHooks` 5, `messages` 4,
  `providerPrefs` 4, `telemetry` 3, `turnStarts` 3, `hookDeliveries` 2,
  `minter` 2, `catalogs` 1, `tools` 1, `lineage` 1, `installed` 1.

The machinery fields cluster cleanly onto the file groups, which is what makes
the split tractable:

| sub-usecase | files today | machinery it owns |
| --- | --- | --- |
| Chat | chat.go, selection.go, handoff.go, chatlog.go | — |
| Runner | agent.go, runners.go, session.go, spawn.go, switch.go | spawns, turnStarts |
| Conversation | turn.go, turn_stall.go, message_record.go, observation.go, terminal_wait.go | turns, work, messages, telemetry, termWait |
| Prompt | prompts.go, prompt_settle.go, catalog.go | prompts, catalogs |
| Hook | ingest.go, hook_delivery.go | pendingHooks, hookDeliveries |
| Answer | answers.go | answers |
| Provider | providers.go, mcp.go | providerPrefs, tools, minter |

Seven, not the six of §3.2. `agent.go` does not survive as a file: it is a mixed
bag whose methods belong to Runner, Chat and Provider respectively.

### C8 — the seams are an artifact of `agent.go`, and there are only five real ones

22 unexported methods are called from more than one file. Measured: **11 of the
14 cross-cluster ones have `agent.go` as a caller**, and `agent.go`'s 29 methods
distribute across all seven clusters (SpawnChat→Runner, MintChat→Chat,
replayStartupHook→Hook, appendTurn→Conversation, providerMCPEnabled→Provider,
threadContext→Chat, …). It is not a concern; it is the residue of the original
split.

Dissolving `agent.go` therefore collapses most apparent coupling. The residual
cross-usecase seams are five:

| seam | method | why it is real |
| --- | --- | --- |
| Prompt → Runner | `spawnRunner` | submitting to a dormant chat must start a CLI |
| Prompt → Runner | `quitOutgoingCLI` | a prompt that displaces a runner must quit the old one |
| Prompt → Conversation | `reconcilePendingPromptFromLedger` | a turn's arrival is what confirms a delivery |
| Prompt → Chat | `chatTurns`, `chatSelection` | prompt assembly reads the conversation and the model choice |
| Chat → Runner | `switchProviderLocked` | changing a chat's provider replaces its CLI |

Five narrow function ports in `deps.go`. quiver.core's own `deps.go` declares
exactly five (`GetArrowFn`, `MarkInstalledFn`, `MarkUninstalledFn`,
`HasDependentsFn`, `ListArrowsFn`) — the same scale, for the same reason.

Prompt is the hub that reaches into three other usecases. That is inherent to
what submitting a prompt does, not an artifact, and it is the one boundary to
watch during S4.

## 10. Fidelity review — draft 1's architecture is largely WRONG

An independent review against quiver.core found four structural errors. I
verified each claim myself before accepting it. Draft 1 §3, §4 and §5 do not
survive.

### R1 — the `internal/` tier is not quiver.core's shape (VERIFIED)

`quiver.core/internal/app/usecases/` contains **exactly one subdirectory, and it
is `mocks`.** There is no `internal/` tier under any usecase.

Where quiver.core actually keeps process-local coordination state — the thing
draft 1 wanted five new packages for:

- inside the store that owns the resource — `engine/vault/store.go:31-34` holds
  `idxMu`, `mu`, and `locks map[string]*sync.Mutex`, with the lazy keyed-mutex
  map at `:154-171`. That is `chatGate`, living in the same file as its store.
- inside the repository — `repositories/runtime/runtime.go:131-133`
  (`drainWg`, `drainMu`, `drainClosed`), passed *down* as a function port.
- **inside the usecase struct itself** — `usecases/discovery.go:93-99` holds
  `mu`, `sessions map[string]*session`, and `listeners`, with cancel, a sweep and
  a grace TTL. That is `catalogRuns` + `chatGate` + `turnWaits` combined, in one
  275-line file, no subpackage.
- a small coordination type gets a **file**: `repositories/discovery/stream.go`
  is 28 lines holding one mutex and one callback.

So `internal/inflight`, `internal/stream`, `internal/answerdesk`,
`internal/catalogrun`, `internal/telemetry` are all wrong. Five packages to hold
five mutexes is a shape quiver.core has nowhere.

**This partly contradicts the instruction that machinery become "an internal/
module".** The resolution is in R2: the decomposition is real, but the unit is a
sibling *usecase package*, not an `internal/` tier beneath one. No package ends
up with 27 files either way.

### R2 — the split axis is the AGGREGATE, and the unit is a sibling package (VERIFIED)

quiver.core sizes a usecase by the aggregate it drives, not by method count:
`ArrowUsecase` 10 methods, `CollectionUsecase` 7, `RuntimeUsecase` 6,
`DiscoveryUsecase` 4, `ConfigUsecase` 2, `SearchUsecase` **1**. A one-method
usecase is fine; six is not a target.

And this repo already follows that convention. `usecases/container.go`:

```go
Project project.Usecase   Folder folder.Usecase   Workspace workspace.Usecase
File file.Usecase         Git git.Usecase         Terminal terminal.Usecase
Worktree worktree.Usecase BranchReview branchreview.Usecase  ...
Agent *agent.Usecase      // the ONLY concrete pointer in the struct
```

Eleven sibling usecase packages, each exporting `Usecase`. The agent package is
the outlier. `repositories/workspace` + `usecases/workspace` already coexist, so
package-name parallelism with the repositories layer is established practice.

**Revised target** — five sibling packages, five container fields, no facade:

| package | drives | today's files |
| --- | --- | --- |
| `usecases/agentchat` | chat aggregate | chat.go, selection.go, parts of agent.go |
| `usecases/agentrunner` | runner lifecycle + prompt submission | spawn.go, switch.go, runners.go, session.go, prompts.go, prompt_settle.go, catalog.go |
| `usecases/agentturn` | activity aggregate: turns, tools, messages, choices, answers | turn.go, turn_stall.go, message_record.go, observation.go, answers.go, ingest.go, hook_delivery.go |
| `usecases/agentread` | query-only, no write ports | chatlog.go, handoff.go, the 11 read methods |
| `usecases/agentprovider` | provider catalog + preferences | providers.go, mcp.go |

`agent.go` does not survive, as established in C8.

### R3 — the embedded-interface facade is invented (VERIFIED)

quiver.core embeds an interface in a struct **zero** times; the six embeddings
that exist are all DTO data embedding. When several usecases must be presented
together it uses **named fields** (`usecases/container.go:14-23`), and a route
group needing two usecases receives **two parameters**
(`api/v0/routes.go:18`).

Draft 1 §3.2 is deleted. `handlers.AgentUsecase` (~30 methods) splits into the
per-concern interfaces the handler files already imply — `activity.go`,
`answers.go`, `chats.go`, `hooks.go`, `providers.go` are already separate files,
each naming a subset.

Two blockers the facade could not have survived, both real:

- `usecase.go:192-198` — `u.tools.Chats = u`, `u.tools.ChatLogs = u`,
  `u.tools.ToolAccess = u.providerMCPEnabled`.
- `terminal_wait.go:47-68` — `newTerminalWaitDetector(u)` wires **six** self-ports
  (`Prompts`, `Notices`, `Work`, `Deliveries`, `Messages`, `OnStall`).

Those methods scatter across four of the six proposed sub-usecases, so under
draft 1 no value would have satisfied `termwait.Deps`.

### R4 — §3.3's closure mechanism is a cycle with a type in front of it (VERIFIED)

quiver.core's named `Fn` types are a constructor-signature readability device.
The internal packages that receive ports take **inline** function signatures
(`repositories/runtime/internal/reactions.go:17-23`), and — decisively — the
closures are always supplied by the **composition root** over a *different*
component (`repositories/container.go:109-139`: `arrowGetter`,
`dependentsChecker`, `catalogLister`). Never sibling-to-sibling within a package.

The correct mechanism is already in this repo, and draft 1 walked past it:
`internal/termwait/termwait.go:20-88` declares **nine** one- and two-method
consumer-side interfaces (`Runners`, `Chats`, `Choices`, `Screens`, `Prompts`,
`Notices`, `Work`, `Messages`, `Deliveries`) plus a `Deps` struct of them.
quiver.core does the same at `usecases/collection.go:20-30`, where the collection
usecase declares a 2-method `arrowCache` over the 24-method repository it is
handed.

**Every cross-package dependency in the split is a consumer-declared narrow
interface, wired from `usecases.Container`.** The five seams of C8 become five
small interfaces owned by the package that calls them.

### R5 — "one type per file" is a `go-style` rule, not a quiver.core one (VERIFIED)

Draft 1 §2.1 imports it from the skill and §2.2 attributes it to quiver.core.
They disagree, measured: `usecases/discovery.go` holds **7** types; `config.go`
5; `repositories/discovery/discovery.go` 6. In this repo,
`internal/termwait/termwait.go` holds **18**.

Resolution adopted: split by **role**, which is what quiver.core actually does
(`search.go` orchestration + `ranking.go` pure scoring are one concern in two
files). A type keeps its tightly-bound satellites — `chatGate` with `gateEntry`,
`messageStreams` with `messageBuffer` — rather than being scattered one per file.
This conflict is flagged for the user rather than silently resolved.

### R6 — accepted additions

1. `export_test.go` per moved package — the repo already uses this
   (`agent/export_test.go`, `turn_stall_export_test.go`); draft 1's "tests move
   with their package" was the worse answer.
2. A `mocks` package per layer; five port sets need five mock sets.
3. `ingest.go:127-149` is a 16-arm switch; quiver.core's idiom for this is a
   dispatch map built at construction (`engine/wizard/wizard.go:63`).
4. Constructor options for a test clock (`WithDiscoveryClock`,
   `vault.NewWithClock`) — several moved types are time-driven.
5. Explicit lifecycle ownership: the sweep, `catalogRuns` cancellations and
   `termWait.Run` own goroutines, and the split must name who stops them.
6. Package doc comments on every new package.

## 11. Feasibility review — what will actually break

A second independent review, AST-measured over the 29 production and 37 test
files. It corrects draft 1's risk ranking in both directions.

### F1 — the headline risk in §7 is fake

All 46 exported methods are methods on **one type**. Go already forbids
duplicate method names on a type, so *any* partition of them is disjoint by
construction. The "embedded-interface method collision" risk cannot fire, and
step I-0 is theatre. Deleted.

The real ambiguity failure is different and worse: with two embedded interfaces
declaring the same name, neither is promoted and **nothing fails at the struct
declaration**. It surfaces only at the satisfaction site — and `agent` cannot
hold that assertion, because `handlers` imports `agent`, so
`var _ handlers.AgentUsecase = (*Agent)(nil)` is an import cycle. The error
would land in `usecases/container.go:63`, reading as a container problem.
`go build ./internal/app/usecases/agent/...` would stay green while the daemon
failed to link. Another reason §3.2's facade is gone (R3).

A nil bucket compiles fine and panics on first call. Any composed surface needs
explicit nil checks in its constructor; the compiler will not help.

### F9 — the agent usecase uniquely violates a law this codebase states out loud
