# Chat Attachments — Design

## Motivation

The native chat surface (Plate-based composer + transcript) has rich Markdown but no attachment support. Users can't paste large blocks of text without it flooding the input as plain prose, can't attach images or files, and can't hand agents an Excalidraw sketch. This design adds four attachment kinds — pasted text blocks, images, files (including CSV-as-table), and Excalidraw diagrams — as **positional, movable, block-level** elements in the composer, insertable via a plus button, drag-and-drop, or paste.

## Non-goals

- No backend wire-format change. The chat message stays a flat markdown string end to end (`{text, clientRequestId}` in, `LedgerTurn.Text string` stored) — attachments are encoded entirely within that string.
- No provider-specific handling. The message text encodes a logical reference to the durable attachment store, not a raw OS path; delivering an actual readable file to a given provider CLI is a uniform materialize-into-worktree step, not per-provider logic (see "Storage & agent delivery").
- No full `BlockMenuKit` feature parity in the composer — attachment blocks get a drag-to-reorder handle, not the rest of its chrome (`/`-insert menu, block-type conversion), which chat deliberately doesn't have (see "Editor UX").
- No editing of Excalidraw scenes rendered in a *read-only* transcript message (only in the composer, before send) — out of scope for v1.

## Attachment kinds

Every kind is a block-level void Plate node with a **resolver**: kind-specific logic for (a) how it's encoded in the message's markdown text and (b) what, if anything, needs to exist as a file for the agent to read.

| Kind | Trigger | Stored as | Markdown encoding | Agent sees |
|---|---|---|---|---|
| Text block | Paste over threshold (Cmd/Ctrl+V only; not inside an existing code block) | Inline in message text (or file if oversized — see Thresholds) | ` ```text-attachment:{id}\n<raw text>\n``` ` fenced block | The raw pasted text, verbatim |
| Image | Paste / drop / "Attach File" picker | File in `chats/{chatId}/attachments/` | `![alt](ref)` — `ref` is a logical reference into the durable store, e.g. `chats/{chatId}/attachments/{file}`, not a raw OS path | Reads the materialized copy at dispatch time |
| CSV (small) | Drop / picker, under a size cutoff **and** cleanly representable (see Thresholds) | Inline in message text | Standard markdown table | Reads the table as text — no file |
| File (PDF, oversized/malformed CSV, other) | Drop / picker, or CSV over the cutoff / not cleanly representable | File in `chats/{chatId}/attachments/` | `[filename](ref)` — same logical-reference scheme as Image | Reads the materialized copy at dispatch time |
| Excalidraw | **Excalidraw** dropdown entry → embedded editor | Inline JSON (or file if oversized); PNG persisted as a normal image file once, when the drawing is finalized | ` ```excalidraw:{id}\n{json}\n``` ` fenced block, plus `![diagram](ref)` pointing at the persisted PNG | Reads the JSON scene as data, and the materialized PNG for a visual read |

Two kinds (text, Excalidraw) never require a stored file under normal size; two (image, generic file) always do. CSV straddles both, resolved by size and shape.

**Why fenced code blocks with special language tags, for text and Excalidraw:** the composer already has a working `CodeBlockPlugin`. Reusing it for `text-attachment` and `excalidraw` tags means no new parser — just a language-tag → custom-renderer mapping (pill+modal for text, diagram-preview for Excalidraw). Each tag carries a generated id suffix (`:{id}`) specifically so a fenced block that merely *mentions* one of these tags in ordinary discussion — including in this repo's own chat, discussing this very feature — doesn't get misinterpreted as a real attachment; the renderer requires the id-shaped suffix, not just the bare tag, and for `excalidraw` additionally validates the content parses as a real Excalidraw scene before treating it as one, falling back to a plain code block otherwise.

**Why `![]()` / `[]()` for images and files, despite needing new rendering work (see "Rendering in the composer & transcript" below):** `MarkdownImageKit`'s parser/serializer already round-trips `![alt](src)` correctly — that part is genuinely free. What is *not* free, and needs building, is actually resolving `src` to visible pixels: no `MarkdownAssetContext.Provider` exists in the chat composer or transcript today (it's wired only into the standalone file editor), and where it does exist elsewhere it resolves workspace-relative paths via an HTTP call, not the kind of reference this feature needs. Reusing the node/syntax shape still avoids inventing a custom container syntax and keeps the agent- and raw-transcript-facing text as ordinary markdown — the win is on encoding, not on rendering, and rendering needs new work either way.

## Rendering in the composer & transcript

Separate from agent delivery, and just as necessary: a human needs to actually *see* an image/file attachment in the composer while drafting and in the transcript afterward. This does not exist today and needs building — it's not a side effect of anything else in this design.

- No `MarkdownAssetContext.Provider` is wired into `chatComposerPlugins` today (interactive composer, interactive transcript message, or static/settled transcript message) — it exists only in the standalone markdown file editor (`markdown-editor-pane.tsx`). Without it, `MarkdownImageElement` falls back to a bare `<img src={rawString}>`, which won't resolve a logical reference like `chats/{chatId}/attachments/{file}` to anything.
- New piece needed: a daemon HTTP endpoint that serves bytes for a given chat's attachment by logical reference (`GET` scoped to `{wsId}/{chatId}/attachments/{file}` or equivalent), and a resolver registered on a newly-added `MarkdownAssetContext.Provider` in the composer/transcript tree that turns `ref` into a fetchable URL for that endpoint. The existing `GET .../chats/{id}/activity/{toolId}/payload?side=...` endpoint (chat-scoped, id-keyed, serves raw bytes for a stored ref) is a closer shape match to follow than either `icons.go` or `readWorkspaceFile` — it just hardcodes `text/plain` since tool payloads are always text, so real content-type sniffing (which `icons.go` already does) is still new work on top of that shape.
- This is a genuinely separate consumer of the same logical reference from agent delivery: the browser fetches bytes over HTTP from the daemon; the CLI subprocess reads a materialized file from local disk. Same `ref` string in the stored markdown, two different resolution paths, neither one substitutes for the other.
- File attachments (non-image) don't need pixel rendering, just a file card (icon by extension, filename, size) — driven by the same logical-reference resolution for metadata (size, existence) without needing to fetch full bytes unless the user explicitly opens it.

## Editor UX

- A plus button sits to the right of the send button, styled neutrally (no primary/green treatment — it's not "the" action). This is real layout work, not a trivial sibling addition: the send/stop control is documented as "one 38px slot with exactly one occupant" in a pixel-precise, field-height-tracking geometry system (`composer-handle.tsx`, `handle-geometry.ts`), already sitting flush at the composer pill's rightmost edge with no reserved space beside it. Fitting a second control in means touching that geometry, not just adding an element next to an existing one.
- Clicking it opens a dropdown with two entries: **Excalidraw** (opens an embedded Excalidraw editor; on save, produces the JSON scene) and **Attach File** (opens a picker that supports both drag-and-drop and click-to-browse; a single entry point regardless of whether the picked file is an image, CSV, PDF, or other — kind is inferred from the file itself, not from which menu entry was clicked).
- Drag-and-drop onto the composer works the same way regardless of entry point. This repo already has drag-and-drop plumbing wired into composer-adjacent components (`pane-container.tsx`, `terminal.tsx`), routed through `extractDroppedFilePaths()` — but that function is currently a dead stub (`file-system-dropped-paths.ts` returns `[]` unconditionally, left out of scope by a prior session). Reviving/repurposing this path is in scope here, not new plumbing from zero.
- Every attachment inserts as a block-level void Plate node at the current cursor position (or drop position, when available).
- "Movable without worries" = a block drag-handle affordance, same interaction shape as `BlockMenuKit` in the full markdown file editor — but that plugin is explicitly excluded from the chat composer today (`chat-composer-plugins.ts` calls it "page-editor furniture"), so this is **new work for the composer**, not a reuse. Scope it as either adopting a composer-appropriate subset of `BlockMenuKit`, or a lighter drag-handle built just for attachment blocks (not full block-menu chrome like `/`-insert or block-type conversion, which chat deliberately doesn't have).
- Paste interception: a paste handler checks (1) is the caret inside an existing code-block node — if so, skip entirely, let it paste as normal code; (2) does the pasted content exceed the text-attachment threshold — if so, wrap it as a `text-attachment` block instead of inserting plain text. Image data in the clipboard always becomes an image attachment (subject to Shift bypass, see below).
- Shift+Cmd/Ctrl+V always bypasses all of the above and inserts plain text, per the original request.

## Storage & agent delivery

Two separate locations, not one — the durable store (permanent, referenced by every message that ever used it, needed for scrollback) and a transient per-turn dispatch copy (exists only while a turn that references it is running, needed so the agent CLI can actually read it — see "Delivery to the agent" below).

- **Location (durable store)**: `{workspaceRoot}/chats/{chatId}/attachments/` — a new leaf under the existing `chats/` sibling directory (`RunnerDir` already nests state under `chats/` today per `worktreepath.go`), not a new top-level pattern. This keeps attachments off `git status` the same way all other chat/agent state already is, and ties their lifecycle to the chat's own lifecycle (deleting a chat already removes `chats/{chatId}`, so no separate cleanup path is needed).
- **Upload endpoint**: new endpoint, needs the same *two* ingestion shapes the existing icon endpoint (`api/internal/api/v0/endpoints/icons/icons.go`) already has, for different attachment sources — not "multipart or base64" (that endpoint doesn't use base64 anywhere): (a) multipart form bytes, for clipboard pastes and browser file pickers, which never have a host filesystem path; (b) a `{"path": "..."}` JSON body naming a local host path that the daemon reads itself, for a revived desktop drag-and-drop (`extractDroppedFilePaths()`) flow, which yields a path, not bytes. The icon endpoint's own code comments flag the path-read variant as a "residual trust assumption" (daemon and webview share a host) it would like to eventually replace with pure byte-upload — worth carrying that same caveat forward rather than treating it as a clean precedent. Not the content-addressed `state/content` store either way (that store is internal to tool-call payloads, not meant to produce a workspace-visible reference).
- **Filenames**: `{shortid}-{originalName}` — the folder is per-*chat*, not per-message, so multiple turns can attach into the same directory; a generated-ID prefix avoids collisions while keeping the original name for display. A clipboard image paste has no original filename (raw bytes + mimetype only) — falls back to a synthesized name (e.g. `pasted-image-{timestamp}.png`, extension from mimetype).
- **Size cap**: needed, exact number TBD in implementation (existing precedents: icons 2MiB, tool-call content store 8MiB; chat attachments likely want a larger ceiling than either given images/PDFs).
- **Delivery to the agent — materialize into the worktree at turn-dispatch time, clean up on turn completion.** This reverses the original plan (direct absolute-path reference, no copy step), on hard evidence rather than the unverified assumption it used to rest on:
  - Neither CLI has any mechanism, at spawn time, for Crowbar to pre-authorize a directory outside the worktree — checked directly against `spawn.go` and both provider descriptor YAMLs (`claude.yaml`, `codex.yaml`); no `--add-dir`-equivalent flag exists anywhere in the spawn/descriptor pipeline.
  - Claude's CLI does have its own native `addDirectories` permission-request suggestion for exactly this situation (read outside its allowed directories) — but Crowbar's answer-relay code cannot currently honor that decision type. `claude.yaml`'s `permission.reply` block only declares `allow`/`deny`/`answer`, and there is a dedicated test (`api/internal/app/usecases/chat/answers_test.go`, `TestAnswer_RefusesADecisionTheProviderCannotExpress`) proving Crowbar rejects an `addDirectories` decision with `ErrInvalidArgument`. So in any permission mode short of a full bypass — and Crowbar deliberately avoids full-bypass modes to preserve its own hook visibility — this read would very likely stall or fail, not succeed.
  - For Codex, whether `--sandbox workspace-write` restricts reads or only writes/network is genuinely unconfirmed by anything in this repo (every piece of sandbox-boundary evidence found discusses writes/shell/network, never reads) — and Codex has no suggestion/escalation mechanism at all (binary allow/deny only), so even if it did turn out to block reads, there'd be no promptable path to approve one.
  - Embedding content directly in the initial prompt instead of a file reference (sidestepping the read entirely) isn't available either — Crowbar's own prompt schema (`vocabulary.yaml`'s `prompt` event) has no image/attachment/content-block field, and neither descriptor's initial-prompt path carries anything but plain text.
  - **Given that, materializing the file inside the worktree removes the question rather than betting on an answer to it**: both CLIs already read/write freely within their own granted cwd as their baseline mode of operation — that's not an assumption, it's how they run at all. The resolver copies each attachment file referenced in a prompt into a scratch location inside the worktree immediately before dispatch, writes that in-worktree path into the markdown, and the runner deletes the scratch copies when the turn completes.
  - **This is genuinely novel for the codebase, not an extension of an existing pattern** — nothing in the spawn/verb pipeline ever writes into `{cwd}` today; every existing `write_file` step targets `{tmp}` (a per-spawn scratch dir under `chats/`, outside the worktree), never the worktree itself. Worth being explicit about rather than implying this reuses something.
  - Turn completion has no single choke point in the runner (normal stop/failure, displacement, runner-exit, and boot-time crash reconciliation all converge through different paths) — so a single "on completion, delete" hook isn't fully reliable on its own. The codebase's existing answer to that same fuzziness for `RunnerDir`'s per-spawn tmp directory is a **dual mechanism**: a normal-exit cleanup callback, *plus* a separate boot-time orphan reap that catches anything a crash left behind (`ReconcileRunnersOnBoot`). This design should mirror that dual mechanism rather than relying on a single cleanup hook — with one complication the implementation plan needs to account for: `RunnerDir` lives outside the worktree (under `chatsDir`), so its existing reap helper's boundary check can't be reused verbatim for a path that's now *inside* the worktree; a new boundary check against the worktree root is needed.
  - Disclosed tradeoff, not hidden: the scratch copy is untracked in `git status` for the duration of an active turn (seconds to a few minutes). No `.gitignore` entry is added for it — that would be writing to the user's own worktree `.gitignore`, which nothing in this codebase currently does, and it would be a permanent marker for a transient file. This is an accepted cost, not an oversight.
  - This applies to every kind that resolves to a real file — image, generic (or oversized/malformed-CSV) file, and the Excalidraw PNG. It does *not* apply to text-attachment, inline CSV, or inline Excalidraw JSON — those stay in the message text itself, never touch the filesystem, and this whole concern doesn't arise for them.
  - **The stored/displayed message text and the text actually dispatched to the CLI are not identical.** `LedgerTurn.Text` always encodes the *durable* logical reference (`chats/{chatId}/attachments/...`) — that's what the browser resolves via the new asset-serving endpoint to render the transcript (see "Rendering in the composer & transcript"; no CLI/sandbox involved on that path) and what stays stable for scrollback and editing. Only at dispatch time does the runner take a copy of that text and rewrite reference to the transient in-worktree path for that specific outbound prompt. The stored message never needs to change based on where a scratch copy happens to live for any given turn.

## Thresholds & fallback rules

- **Paste-to-text-attachment**: proposed default >400 chars or >6 lines collapses to a pill; shorter stays plain inline text. Tunable, not architectural. Does not trigger if the caret is inside an existing code block.
- **CSV table-vs-file**: two independent gates, both must pass for inline-as-table. (1) Size: small enough to render as a reasonable markdown table (rows × columns), exact cutoff TBD. (2) Shape: parses cleanly with a real CSV parser (RFC4180 — quoted fields, embedded commas/quotes) *and* no cell contains a newline or an unescapable `|` that would corrupt GFM table syntax. Since inline CSV is delivered as text the agent reads as ground truth, a naive comma-split here isn't just a display bug — it would hand the agent silently-corrupted data. Failing either gate falls back to a file attachment, never a best-effort/corrupted table.
- **Inline-size cap (text, Excalidraw)**: the client-side prompt queue caps a message at 64KB (`MAX_PROMPT_TEXT_BYTES`, `prompt-queue-persistence.ts:29`). Since text-attachment and Excalidraw both default to inline encoding, either can exceed that cap. Fix: apply the same "small enough → inline, else → file" rule CSV already uses — an oversized paste becomes a `.txt` file attachment instead of an inline pill; an oversized Excalidraw scene becomes a `.excalidraw.json` file instead of a fenced block. One shared size check, reused across all three inline-capable kinds, rather than three separate ad-hoc rules.
- **Oversized file/image drop** (exceeds the size cap): rejected at the picker/drop handler with an inline error; nothing partial gets inserted.
- **Unsupported/unknown file type**: no special-casing — falls through to a generic file card (icon by extension, filename, size).
- **Missing attachment on reload** (file deleted from disk out-of-band): the image/file node renders a broken/missing placeholder rather than failing the whole message. `MarkdownImageKit` likely already needs to handle a broken relative image path today, so this is an existing concern being extended, not a new one.
- **Orphaned files from discarded drafts**: image/file attachments upload eagerly on attach (paste/drop/pick), before send. If the user removes the attachment from the draft, or discards the draft entirely, the uploaded file is already on disk with nothing referencing it. Accepting this as a known gap for v1 (no GC) rather than solving it now — worth a line in the implementation plan, not a blocker for the design.

## Open questions for the implementation plan

- Composer drag-handle scope: adopt a `BlockMenuKit`-equivalent subset, or build a lighter drag affordance scoped just to attachment blocks (composer deliberately lacks the rest of `BlockMenuKit`'s chrome — `/`-insert, block-type conversion — so a full adoption isn't a clean drop-in).
- Exact byte/char/line/row thresholds for: paste-to-pill, CSV table-vs-file, inline-vs-file size cap.
- Exact upload endpoint request/response contract for both ingestion shapes (multipart bytes, host-path read).
- Exact contract for the new attachment-serving GET endpoint the frontend asset-context resolver calls.
- Which turn-lifecycle hook (completion/abandonment/interruption) triggers dispatch-scratch-copy cleanup.
- Excalidraw library choice and version; whether the embedded editor is a modal or an inline panel.
- Exact Plate node/component names and where they live among the three existing `plate/` directories (composer vs transcript vs markdown editor) given `chatComposerPlugins`/`chatComposerPluginsStatic` are shared between composer and transcript rendering; same question for where the new `MarkdownAssetContext.Provider` gets mounted so it covers all three composer/interactive-transcript/static-transcript render sites.
- Which CSV parser to use for the RFC4180-correctness gate.
- Whether the fence-tag `{id}` (text-attachment, excalidraw) and the filename `{shortid}` are meant to be the same generated value (relevant for Excalidraw specifically, since one attachment uses both — a fence-tag id for the inline JSON and a filename shortid for the persisted PNG) or independent ids. The frontend already has `nanoid` in real use for short opaque ids (`pane-layout.ts`, `buffer-slice.ts`) as the natural generator either way; the backend has no equivalent (ids there are full UUIDs), so if these need to match, the client mints the id and passes it through rather than the server generating it.
- Whether "Attach File" needs any client-side mimetype allowlist/denylist, or accepts anything.
- Plus-button placement within the existing composer geometry system (`composer-handle.tsx`/`handle-geometry.ts`).

## Testing considerations

- Paste interception: threshold boundary behavior, codeblock-context exception, Shift-bypass, image-in-clipboard.
- Resolver correctness per kind: inline vs file fallback at size boundaries, markdown round-trip (encode → parse → re-render matches original).
- Drag-and-drop: revived `extractDroppedFilePaths()` path, drop-position insertion.
- Missing-file placeholder rendering (simulate a deleted attachment).
- Upload endpoint: size cap rejection, filename collision handling, both ingestion shapes (multipart, host-path).
- Asset rendering: composer and both transcript render modes (interactive, static) actually show a real image, not a broken-image fallback; asset-serving endpoint access scoping.
- Fence-tag collision: a plain ` ```text-attachment ` or ` ```excalidraw ` fenced block *without* a valid id suffix (or, for excalidraw, without valid scene JSON) renders as an ordinary code block, not hijacked as an attachment.
- CSV correctness gate: quoted fields with embedded commas/newlines, unescapable `|`, all correctly fall back to file rather than producing a corrupted table.
- Dispatch/cleanup lifecycle: materialized scratch copy exists for the full duration of a multi-step turn (not deleted early), and is actually cleaned up on completion, failure, and interruption alike.
